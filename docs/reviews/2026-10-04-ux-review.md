# Mizan: hands-on usability review

Reviewed 4 October 2026. Repository: https://github.com/ImSleepingHere/Mizan
Commit: `034afcb2c5e33882536ffc092267d6e42636dec5`.

## Scope and confidence

I ran an isolated copy with synthetic demo data and used the student, professor, and scheduling committee workspaces. I explored timetables and search; evaluated meeting changes; searched common free times; generated an instructor improvement; approved and published it; and inspected stale proposals, placement analysis, diagnostics, staffing, settings, Arabic UI, and audit records. No live university records were changed.

The frontend built successfully. Temporary launch/proxy changes were needed for this review environment. The local AI service and Windows OCR were unavailable, so their successful end-to-end behavior was not evaluated. A whole-semester optimization attempt failed in this environment; its root cause was not established. Mobile devices, a full screen-reader audit, production-scale performance, and export fidelity were not assessed. This is a hands-on audit of the exercised workflows, not an exhaustive certification.

Entries below separate observed behavior from proposed improvements. P1 means fix before relying on the affected workflow; P2 means substantial everyday friction; P3 means useful polish. These priorities describe usability, not security severity.

## What works and should be preserved

- The core proposal → approval → publication workflow worked for a real instructor improvement, advancing Faculty week from v1 to v2.
- The backend rejected approval of an outdated proposal, protecting the current timetable.
- Conflict checking exposed collisions and previewed student impact.
- Instructor optimization produced a concrete before/after meeting change and quantified benefits and adverse effects.
- Existing timetable filters help narrow the schedule. Keyboard Enter opens class details, and Escape closes the proposal modal.
- Placement analysis already explains that compatible students are not allocated seats. Preserve that distinction while improving presentation.

## Student experience

### S01 · P1 · Clicking a class does not open its details
**Observed:** The timetable instructs “Tap a class to see its details.” Pointer clicks did not open the drawer; focusing a class and pressing Enter did. This is a pointer interaction defect, not a missing details feature.
**Improve:** Make click, tap, and Enter open the same details view for read-only roles. Ensure editing drag behavior cannot swallow normal clicks.
**Done when:** A student can open every class with pointer and keyboard and close it without losing their position.

### S02 · P1 · Occupancy numbers are misleading
**Observed:** Student classes displayed “1 / 80 enrolled.” The scheduler’s baseline S001 showed 75 / 80. The student response contains only the signed-in student, while displayed enrollment is calculated from the available student collection.
**Improve:** Return a safe aggregate occupancy count independently of roster visibility, or hide occupancy when authoritative totals are unavailable. Do not expose the class roster to fix this.
**Done when:** Occupancy for the same section agrees across roles while student data remains restricted.

### S03 · P2 · Faculty are presented as internal IDs
**Observed:** Student list/details used identifiers such as P001 rather than instructor names. The student response omits professor records.
**Improve:** Include permitted instructor display names with section details. Keep IDs secondary for support and disambiguation.

### S04 · P2 · The landing page delays the main student task
**Observed:** Metrics and a large Edugate export panel precede the timetable.
**Improve:** Lead with “Today,” the next class, time, location, and the weekly timetable. Move export into a compact action. Surface any published change affecting the student near the relevant meeting.

### S05 · P2 · Quality labels do not explain the student’s actual problem
**Observed:** Weekly gap 10h was Critical, longest gap 120min was Good, and quality 45 was Critical. These can use different scales, but the interface does not make those scales understandable.
**Improve:** Define each metric, its time period and threshold. Add concrete explanations such as “You have a two-hour break on Sunday.” Avoid presenting a score without explaining what could improve it.

### S06 · P2 · Eligible sections are difficult to turn into a decision
**Observed:** The conflict-free options form a long list with repeated courses and section IDs, with no clear comparison or continuation.
**Improve:** Group by course; search and filter; compare alternatives by campus days, gap changes, instructor and available capacity. Add a shortlist or schedule preview and explain whether an option is merely a suggestion or can be acted on elsewhere.

### S07 · P2 · Search does not explain an empty result
**Observed:** In list view, “Highlight classes” and another search field mirror the same query. Searching for nonexistent text leaves an empty table without a no-results message, while the section/meeting count still describes the total schedule.
**Improve:** Use one clearly labeled search control. Show “No classes match …,” a Clear search action, and “0 of 5 sections” when filtered.

### S08 · P3 · Demo scenarios compete with the official schedule concept
**Observed:** Students can select baseline and diagnostic scenarios in the demo.
**Improve:** Clearly label the demo scenario chooser. In a real workspace, distinguish the current published timetable, historical versions and any previews. Do not make a student infer which schedule is authoritative.

## Doctor / instructor experience

### I01 · P2 · The main teaching workspace is hard to discover
**Observed:** The instructor starts at Change requests; their timetable and My classes are under “Semester lab.”
**Improve:** Start with “My teaching week,” pending requests and clear actions. Use task names such as Timetable, Find a meeting time, and My requests.

### I02 · P1 · An unchanged meeting becomes a reviewable proposal
**Observed:** In Faculty week, evaluating S087 at its existing Sunday 10:00 time created proposal 0cf13dbd6e7f, marked Ready for review, with zero section changes and zero hours of improvement.
**Improve:** Detect identical before/after values and explain “This meeting is already scheduled at that time.” Do not create a request.
**Done when:** A no-op cannot enter the committee queue. See `mizan-ux-no-change.jpg`.

### I03 · P1 · “Evaluate” silently submits persistent work
**Observed:** Evaluate change creates a persisted proposal. This happened for unchanged and conflicting changes as well as meaningful ones.
**Improve:** Separate “Preview impact” from “Send for review.” Show current versus proposed meeting, impact and conflicts before the instructor intentionally submits. Clearly identify saved drafts if previews are persisted.

### I04 · P2 · Change forms hide important constraints
**Observed:** The reason field relies on native “Please fill out this field” validation rather than visibly marking it required. Start time is prominent, but resulting end time/duration is not. Late start options can imply an end beyond normal hours; backend acceptance of that case was not tested.
**Improve:** Mark required fields, give a reason example, show end time live, and restrict or explain invalid time choices.

### I05 · P2 · Conflict explanations repeat technical codes
**Observed:** Moving S087 to Sunday 08:00 produced 12 conflicts with repeated entries such as STUDENT_OVERLAP and S001 · S087. Multiple affected students generate visually repetitive messages.
**Improve:** Group by conflicting class pair and meeting, show the number of affected students, and provide “Show on timetable.” Lead with plain language; retain codes only in expandable technical details. When no alternative is available, say so explicitly.

### I06 · P2 · Section selection requires memorizing IDs
**Observed:** Common-time search checkboxes display section IDs such as S087 and S088.
**Improve:** Show course name, section, instructor and meeting summary. Add search/select-all for larger teaching loads.

### I07 · P1 · Common-time results remain valid-looking after inputs change
**Observed:** Searching S087 for 60 minutes returned results for 35 students and 60 minutes. Adding S088 and changing duration to 120 minutes left those old results displayed without a stale warning.
**Improve:** Clear results or mark them “Out of date—search again” immediately on any criteria change. Display the exact criteria used for each result set.
**Done when:** No result can be mistaken for an answer to the current inputs when it was calculated from earlier ones.

### I08 · P2 · A useful free slot is a dead end
**Observed:** Results show possible slots but provide no direct copy, shortlist or next-step action; the interface correctly says the search books nothing.
**Improve:** Offer Copy suggestion, Save shortlist, or prefill the applicable request workflow. Explain what happens next and who can confirm the time.

### I09 · P3 · Unchecked days mean all days
**Observed:** “Days (none = any)” requires interpretation.
**Improve:** Use an explicit All days default and clearly show when a restricted selection applies.

### I10 · P2 · AI availability is revealed too late
**Observed:** Ask Mizan accepts text and an Understand action, then reports that the local model service must be started.
**Improve:** Show service availability before the user invests effort, preserve their text, and link to the equivalent manual form. Successful interpretation quality was not tested because the service was unavailable.

### I11 · P1 · Moving into Change requests loses the proposed destination
**Observed:** In S087 details, I chose Tuesday 11:15 and checked the move. “Open in change requests” opened the original Sunday 10:00 values instead of the destination just evaluated.
**Improve:** Carry section, meeting identity, proposed day/time and any reason through the handoff. Show a persistent before → after summary.
**Done when:** A checked move reaches the next screen unchanged and can be submitted without re-entry.

### I12 · P2 · Similar actions have unclear differences
**Observed:** Check, Stage move, Open in change requests and Evaluate change appear across related workflows.
**Improve:** Standardize on a small sequence: choose change → preview impact → submit request. Explain when a staged move is local, saved or submitted.

### I13 · P1 · An instructor cannot easily find their own optimization later
**Observed:** Improve my classes produced proposal 186804788e9b, moving S091 from 08:00 to 14:00 on Monday/Wednesday. It reported 228 student-hours saved, 27 students benefiting and 2 worsening. After navigating away, the instructor’s Change requests list showed meeting-change requests but not this optimization. The committee could see it.
**Improve:** A unified My requests list must include all proposal types with status, submitted time and a permanent detail link. The success state should offer View request.
**Done when:** An instructor can leave, return and track the same proposal through approval and publication.

### I14 · P2 · Navigation discards work in progress
**Observed:** Returning to Semester lab reset common-time criteria and cleared the Ask Mizan text.
**Improve:** Preserve drafts and search criteria within the session. Warn before discarding meaningful unsent changes; allow an explicit Reset.

### I15 · P2 · Institution-wide statistics obscure a local teaching decision
**Observed:** A proposal concerning the instructor’s classes showed institution-level figures such as 13,839.5 gap hours and 1,407 students with long gaps.
**Improve:** Show affected classes and students first, with before/after details and adverse cases. Keep institution totals as secondary context with explicit scope labels.

## Scheduler / scheduling committee experience

### C01 · P2 · Approval does not clearly lead to publication
**Observed:** Approval closed the modal and displayed “Decision saved. The audit trail has been updated.” Publishing required reopening the approved card.
**Improve:** Keep the result visible with “Approved—not yet published,” Continue to publication and View proposal. Make the live timetable version explicit.

### C02 · P1 · Stale requests still advertise “Ready for review”
**Observed:** After publishing Faculty week v2, the older proposal still appeared Ready for review with an enabled Approve action. Clicking it returned “Stale proposal: timetable changed. Evaluate a new proposal.” The backend correctly blocked it, but the UI retained the misleading state and displayed duplicate error areas.
**Improve:** Mark outdated proposals before interaction, disable invalid approval, show the revision mismatch, and offer Re-evaluate against current timetable while retaining the requested change.
**Done when:** The queue accurately distinguishes actionable and stale work. See `mizan-ux-stale-proposal.jpg`.

### C03 · P2 · The review queue is difficult to scan
**Observed:** Cards emphasize generic proposal type, hash, revision and aggregate totals. They lack a concise requester/class/time narrative and useful filtering.
**Improve:** Lead with “Dr. [name] requests [course] Sunday 10:00 → Tuesday 11:15.” Add submitted time, status tabs, search, sort and affected-cohort filters. Keep identifiers secondary.

### C04 · P1 · Harm and benefit need clearer decision language
**Observed:** Advanced metrics such as Gini and worst decile appear without accessible definitions. A Students worsened value of 2 received a green Strong rating. Adverse rows such as “ST0016 · 120 gap minutes · 0 campus days” do not clearly distinguish deltas from totals.
**Improve:** Present benefit and harm separately with neutral or cautionary styling for harm. State “+120 gap minutes/week; no additional campus days,” and provide before/after days and affected meetings. Explain aggregate fairness metrics in expandable help.

### C05 · P2 · The complete timetable becomes unreadable
**Observed:** All sections displays 100 sections / 200 meetings as very narrow overlapping cards, some effectively unreadable. Filters help; the issue is the all-sections view, not every filtered view.
**Improve:** Use a density overview at this scale, then drill down by cohort, instructor, room or day. Offer readable resource lanes and zoom. Do not shrink text cards indefinitely.
**Evidence:** `mizan-ux-crowded-timetable.jpg`.

### C06 · P2 · Planning tools push the timetable down the page
**Observed:** Import/export, common-time and AI panels stack before the timetable.
**Improve:** Give the timetable the main workspace. Put tools in a side panel or task tabs and place records/import management in its own area. Preserve the visible date/filter context while using a tool.

### C07 · P2 · Scheduler inputs depend on internal IDs
**Observed:** Scheduler free-slot search accepts section IDs as free text.
**Improve:** Use a searchable section picker with course, cohort and instructor labels, immediate unknown-ID validation, and a clear selected-sections summary.

### C08 · P2 · Placement options are hard to compare
**Observed:** Course placement uses a long dropdown of roughly 80 courses and returns numbered options with IDs such as R003/P002. Later options can show more compatible students and larger gap benefits than earlier ones, without a clear ranking explanation. Counts such as 1,350 compatible students appear beside an 80-seat room; an existing disclaimer correctly distinguishes compatibility from allocation.
**Improve:** Search courses, explain and control sorting, and show resource names. Separate hypothetical benefits across all eligible students from capacity-limited estimates. Add compact trade-off comparisons and expandable resource constraints. Do not imply all compatible students will be enrolled.

### C09 · P2 · Invalid baselines lead users into a blocked action
**Observed:** Baseline diagnostics showed 159 violations, while Optimize remained prominent. Running it returned INVALID_BASELINE: Resolve hard violations before optimization.
**Improve:** Promote Fix conflicts when the baseline is invalid. Provide a grouped, actionable violation list linked to the timetable, with progress toward an optimizable state.

### C10 · P1 · Service failures are not recoverable from the UI
**Observed:** An initial connection problem surfaced as a raw JSON parsing error. A later whole-semester optimization attempt also produced a JSON error and left scenario loading unusable until the review backend was restarted. This environment may have caused the failure; solver correctness or production reliability cannot be concluded from it.
**Improve:** Explain service unavailable/request failed in normal language. Show optimization progress, elapsed time, safe cancellation where supported, and Retry. Preserve criteria and the last usable timetable. Handle non-JSON error responses robustly.

### C11 · P2 · Disabled settings do not explain role permissions
**Observed:** The committee account sees disabled policy controls and Save without a clear nearby explanation.
**Improve:** Show “Read-only: administrators manage scheduling policy,” identify the responsible role, and provide a clear handoff. Label controls that do not affect the current optimization mode so users understand their scope.

### C12 · P2 · Staffing analysis lacks an actionable continuation
**Observed:** The shortfall view and a long workload table provide information, but no obvious next task for the committee. The workload table is difficult to narrow to relevant qualified or overloaded faculty.
**Improve:** Filter by qualification/course/load, connect shortfalls to candidate staff and affected sections, and identify the owner of the next decision. This is a workflow presentation recommendation, not a claim that automated hiring or reassignment already exists.

### C13 · P2 · Audit entries lack context
**Observed:** A globally visible publication event from Faculty week appeared while the selected header scenario was Baseline. Entries emphasize action, role and hash without a useful linked change summary.
**Improve:** Label the audit’s scope explicitly. Include scenario, version, actor, affected sections and a link to the corresponding proposal. Add scenario/date/action filters.

## Across roles

### X01 · P2 · Error messages remain after leaving the failed task
**Observed:** A previous JSON error remained visible on unrelated settings/staffing screens.
**Improve:** Scope errors to their operation, provide a clear dismiss action, and clear resolved errors after successful retry. Avoid duplicate background banners and toasts for one failure.

### X02 · P2 · Pages cannot be reliably resumed or linked
**Observed:** Navigation remains at the root URL and workspace state resets on a fresh load. A specific proposal or working screen has no obvious stable link.
**Improve:** Give key views and proposal details stable routes; preserve meaningful filters and selected scenario. Make browser Back/Forward restore the expected context.

### X03 · P2 · Animated decision numbers briefly mislead
**Observed:** Counters animate from zero on mounting, temporarily showing zero worsened students or partial savings before reaching final values. This is transient, not a persistent calculation mismatch.
**Improve:** Render exact impact values immediately in approval and publication dialogs. Reserve decorative counting for noncritical dashboards, respecting reduced-motion preferences.

### X04 · P3 · Arabic coverage is incomplete
**Observed:** Arabic layout/text exists, but role strings, technical backend errors and some accessible labels remain English.
**Improve:** Localize errors and accessible control names as well as visible headings. Review mixed-direction course IDs and times with Arabic-speaking users. This review was not a full linguistic or screen-reader audit.

### X05 · P3 · The account-name control signs out unexpectedly
**Observed:** Clicking the displayed account name immediately logs out.
**Improve:** Use an explicitly labeled Sign out control or open an account menu with a separate sign-out action.

### X06 · P2 · Record browsing does not scale beyond a truncated set
**Observed / source-supported:** The records UI notes a maximum of 100 matching records; the implementation limits the returned/displayed set without a normal pagination workflow. Not every record type was exhaustively exercised.
**Improve:** Show total matches, pagination or deliberate incremental loading, sort controls and domain-relevant columns. Keep search, but do not make users guess search terms just to reach later records.

## Recommended implementation order

1. **Restore trust in state:** S01, S02, I02, I03, I07, I11, I13 and C02. These affect whether the user can open, understand, submit or recover the intended work.
2. **Make decisions safe to understand:** C04, C10, X01 and X03. Show exact impact, readable harm, and recoverable failures.
3. **Build coherent role workspaces:** S04, I01, I12, I14, C01, C03, C05, C06 and X02.
4. **Make discovery and analysis efficient:** names instead of IDs, grouped conflicts, useful search and empty states, placement comparison, actionable diagnostics and staffing.
5. **Finish consistency:** localization, labels, permissions explanations and remaining polish.

## Three acceptance journeys to use after improvements

**Student:** Sign in → identify the next class → click it → read instructor, room and accurate occupancy → search for an alternative course section → compare its effect on the week → clear search without losing context.

**Instructor:** Open My teaching week → choose a meeting → preview another time → understand grouped conflicts → intentionally submit → navigate away → find the same request → see its current review/publication status. Repeat common-time search after changing both participants and duration; no stale results should appear current.

**Scheduler:** Open an actionable queue → understand requester and before/after changes → inspect benefiting and worsened students → approve → publish with a clear version transition → see competing old proposals become stale immediately → re-evaluate one without retyping its intent. For an invalid baseline, follow a conflict directly to a repairable meeting.

The next usability round should include real student/instructor/scheduler participants, phone layouts, keyboard-only and screen-reader use, large datasets, and working AI/OCR services. Those are remaining validation tasks, not observed failures in this review.
